# Hub matching scale benchmark protocol

This protocol requires an isolated PostgreSQL instance and Hub/worker deployment; it never resets a database. No results are supplied or implied. Start from the commands in `hub-push-benchmark-2026-11-14.md`, using a fresh isolated database, the same schema and seed dataset in both arms, fixed matching partitions and dedicated CPU. Enable pg_stat_statements at server start. Configure baseline candidate matching and tuned candidate matching on otherwise identical hosts; record commit, migrations, hardware, runtime versions, all flags and CPU limits. Restart only the isolated benchmark processes between arms. Use a unique run ID for each trial, never reset pg_stat_statements on a shared server.

For each arm, provision 8, 400 and 4000 logical worker lanes; verify registered sessions match the intended count. For each lane count run idle (no ready work), burst, sustained backlog and a single hot constrained resource. The existing `scaling/benchmarks/hub-push-load.py` and `hub-push-metrics.sql` measure onboarding burst/end-to-end and durable schedule-to-start latency. Use a fixed number of submissions and VUs for burst; for sustained backlog use a larger fixed count and VU level and sample PostgreSQL ready depth throughout, rejecting any run without sustained backlog. Set `WFC_BENCH_SHARED_TENANT=true` for the hot constrained workload: the sample provision activity uses a capacity-one strict FIFO tenant resource. For other cells unset it. For idle, leave worker lanes connected without submitting work. Keep offered load, task mix, duration, resource policy and dataset identical across arms. Warm each cell, then take five independent measured runs; preserve raw run artifacts and failed runs. Do not compare if warmup or any trial failed.

Snapshot database-scoped pg_stat_statements calls for acquisition SQL, pg_stat_database transaction counts, pg_stat_wal wal_bytes, and Hub plus PostgreSQL process CPU time immediately before and after each run. Use an otherwise idle isolated database/server so WAL and CPU deltas are attributable; record any resets or counter rollover as invalid. Divide deltas by durable completed task counts from `hub-push-metrics.sql`, and collect p95 schedule-to-start and completion throughput. For idle runs record statement calls divided by measured seconds. Keep per-process CPU time rather than instantaneous CPU percent; do not substitute offered workflow rate for completed tasks. Snapshot queries and exact acquisition query IDs must be archived with raw pg_stat_statements outputs because query IDs and SQL vary by mode.

Create a JSON array with one object per run: `mode` (`baseline` or `tuned`), `lanes` (8, 400, 4000), `workload` (`idle`, `burst`, `backlog`, `constrained`), `warmup` (boolean), `repetition` (unique within a measured cell), `ok` (boolean), `seconds`, `acquisition_statements`, `matching_statements` (all matching queries, including discovery and acquisition), `transactions`, `wal_bytes`, `cpu_seconds`, `completed_tasks`; non-idle entries also require `throughput` and `schedule_start_p95_ms`. Run `python scaling/benchmarks/hub-matching-scale-analyze.py trials.json --output analysis.json`. It fails closed for incomplete cells or failed acceptance gates; it reports medians, per-task costs and the requested thresholds. Supplement it with raw snapshots and configuration; a passing aggregate is not a substitute for correctness/failover tests. No benchmark has been run for this change.
