# PostgreSQL index, write, and CPU review: two 4,000-workflow bursts

**Scope.** Independent review of PostgreSQL index/write amplification, settings, and CPU interpretation for the 14 November 2026 17:15–17:20 UTC evidence window. This report does not change runtime code or database state. The supplied review at [`postgresql-4k-review-2026-11-15.md`](../postgresql-4k-review-2026-11-15.md) is a starting hypothesis set; measurements below are checked against the archived `evidence.json`, current source/migrations, and a short read-only inspection of the shared PostgreSQL container. The latter is a later snapshot and must not be confused with the five-minute window.

## Ranked findings

### 1. Task state transitions are a credible write-amplification target; index removal is not yet justified

**Measured:** the task table has 21 indexes in both the archived index snapshot and the live catalog. Its live heap+index size was about 203 MiB (`pg_total_relation_size=213,221,376` bytes), estimated 64,000 rows. The archived cumulative index snapshot, reset at 16:49 UTC and therefore spanning four runs rather than just the target window, attributes 20,584,374 heap fetches to `ix_hub_task_claim_sequence` and 8,262,274 to `ix_hub_task_claim_hub_sequence`. Those are cumulative heap fetch counters, not unique tuples, disk reads, or CPU. In the target window, the completion update took 19.91 s and insertion of the next task took 14.35 s in `pg_stat_statements` elapsed execution time; elapsed time is not CPU attribution.

The later live `pg_stat_user_tables` snapshot reports 144,000 task updates, zero HOT updates, and 842 dead tuples since the same approximate reset. This aggregate spans multiple bursts and background activity. It is consistent with, but does not prove per-statement index churn. `state` is a predicate column in numerous partial task indexes (migrations 007, 012, 020–029); completion changes it from leased to complete ([`HubTaskStore.cs`](../../src/WorkflowCore.Hub/HubTaskStore.cs#L1247)), and retry changes both state and due time ([same file](../../src/WorkflowCore.Hub/HubTaskStore.cs#L1281)). Updates that change an indexed key or a partial-index predicate cannot use HOT. The observed zero HOT updates is therefore plausible for this workload. Next-task INSERTs must also insert an index entry for each applicable index. These are concrete structural write costs, but the data do not isolate their fraction of the 19.91 s / 14.35 s statement totals.

**Interpretation / hypothesis:** pruning redundant optional indexes could lower insert and state-transition work. The 21-index count alone does not establish harmful overhead, and the broad claim indexes' large fetch totals do not show they were used in the target five minutes or that they dominate CPU. Keep uniqueness and foreign-key support intact. First test retirement only in an isolated, representative backlog benchmark.

### 2. Broad claim indexes merit a controlled retirement test, with legacy-path coverage as a gate

Migration 022 creates a partial sequence index and drops earlier active indexes; 023 adds `(hub_id, sequence)`; 025–028 add increasingly specific capability/bucket/shard indexes; 029 adds the current candidate-discovery indexes ([migration 022](../../sql/022_hub_claim_index_selectivity.sql#L3), [023](../../sql/023_hub_claim_hub_sequence.sql#L3), [025](../../sql/025_hub_claim_capability_sequence.sql#L3), [026](../../sql/026_hub_matching_bucket_claim_index.sql#L7), [027](../../sql/027_hub_ready_claim_indexes.sql#L3), [028](../../sql/028_hub_claim_shard4_ready.sql#L5), [029](../../sql/029_hub_partition_candidate_indexes.sql#L3)). This sequence of alternatives makes overlap likely, but not sufficient evidence to drop any index.

The archived four-run index counters show substantial broad-index reads. In the later live catalog, both broad indexes remain valid and ready; the sequence-only one is about 1.0 MiB and hub+sequence about 2.0 MiB. Both are optional non-unique indexes. Current candidate admission is by selected task IDs/observed epochs and a primary-key join, with transactional eligibility rechecks, row locking, and `SKIP LOCKED` ([`HubTaskStore.cs`](../../src/WorkflowCore.Hub/HubTaskStore.cs#L645)); the current candidate reader instead pages by hub/bucket/deadline-or-sequence ([`HubCandidateReader.cs`](../../src/WorkflowCore.Hub/HubCandidateReader.cs#L50)). The retained legacy SQL candidate path still orders/filter-scans tasks by capability, readiness, partition and sequence ([`HubTaskStore.cs`](../../src/WorkflowCore.Hub/HubTaskStore.cs#L432)). It may use capability or broad compatibility indexes depending on configuration, hub count, bucket count, and plan choice. `pg_stat_user_indexes` gives accumulated planner use, not proof that a query path is retired.

### 3. CPU was real work but does not warrant infrastructure tuning by itself

The archived window records estimated PostgreSQL CPU of 385.15 CPU-seconds over 300 seconds, averaging about 1.28 cores, with a one-minute peak of 328.72% (3.29 cores). Against the reported 16-CPU Docker VM, the peak is about 20.5% of VM CPU capacity. The two runs each completed 4,000 workflows / 16,000 tasks without extra attempts. This denominator is intentionally workload-level: the CPU series includes PostgreSQL background work and post-run audits, so 385.15 / 8,000 = 48.14 ms per completed workflow (12.04 ms/task) is an all-window allocation, not a per-workflow execution cost. Other containers share the VM. The sample does not show VM-wide saturation or justify adding CPU, changing quotas, or tuning PostgreSQL process count.

The 129.27 seconds of sampled statement elapsed time is not a CPU counter and must not be subtracted from CPU-seconds to estimate unexplained CPU. Lock waits, concurrent overlaps, planning, background work, and query-stat sampling mean the values measure different things. Likewise, table `idx_tup_fetch` is heap access via indexes, not unique rows or physical I/O. CPU should be revisited only if throughput/SLO degrades or a controlled A/B shows CPU pressure at equal work and completion latency.

### 4. Current defaults are not evidence of a cache or memory bottleneck

A read-only live `pg_settings` inspection returned `shared_buffers=128MB`, `work_mem=4MB`, `effective_cache_size=4GB`, `autovacuum=on`, vacuum/analyze scale factors 0.2/0.1, `autovacuum_naptime=60s`, `maintenance_work_mem=64MB`, `effective_io_concurrency=1`, and `random_page_cost=4`. The Docker VM was reported as 16 CPUs / about 31.2 GiB, but that is not a PostgreSQL container memory limit. Defaults may be conservative, yet changing them without container memory accounting and isolated measurement is guesswork.

In the later live table snapshot, `hub_task` had 842 dead vs 64,000 estimated/live tuples, with autovacuum and autoanalyze recorded during the burst interval; workflow had 421 dead vs 16,000 live, also with autovacuum/autoanalyze. The burst may have briefly produced more dead tuples before vacuum. This does not establish vacuum lag or bloat. The window's leading sampled statements had no temp blocks written in the baseline snapshot; selected read-heavy work was mostly shared-buffer hits. Neither result rules out storage latency, but there is no evidence here for increasing `shared_buffers`, `work_mem`, `effective_cache_size`, changing durability, disabling sequential scans, or weakening autovacuum.

## Concrete proposed change (not implemented)

Use a branch-only index-retirement experiment before writing a production migration. Candidate pseudodiff after the tests below pass:

```sql
-- Migration 031 experiment only; do not apply to the shared stack yet.
DROP INDEX CONCURRENTLY IF EXISTS wfc_scale.ix_hub_task_claim_sequence;
-- In a separate A/B arm, test removal of claim_hub_sequence instead;
-- test removal of both only after each single-index arm preserves all paths.
```

If adopting a migration, use an expand/observe/contract rollout: first ship a version that no longer relies on the candidate index on every Hub and legacy claim mode; collect at least one representative maintenance/recovery cycle; then drop concurrently in a dedicated migration runner (outside a transaction if required by PostgreSQL). Keep a rollback migration that recreates the exact definition. Concurrent index creation/drop avoids a long blocking lock but still performs I/O and should be scheduled and measured. This is a proposed test direction, not a proven optimization. Do not include the uniqueness indexes, candidate-reader indexes, or monitor index in the first arm.

## Experiment and acceptance plan

All tests below are **unverified**; no live backlog profiling or load was run for this report.

1. **Read-only plan triage on isolated data:** restore or generate a production-shaped snapshot with the same 64k task/history scale and realistic state mix. Capture `EXPLAIN (COSTS, SETTINGS, FORMAT JSON)` (no `ANALYZE`) for legacy claims, candidate discovery, monitor list/summary, expiry/recovery, workflow retirement, and native reconcile using migrations 007–030. Reserve `EXPLAIN (ANALYZE, BUFFERS, ...)` for the isolated executed benchmark below; do not run it against live mutating SQL.
2. **Isolated backlog A/B:** same data snapshot, Postgres major/config, history, Hub/worker counts, and two 4,000-workflow bursts; repeat control and each index arm in bracketed order. Arms: baseline; drop only `claim_sequence`; drop only `claim_hub_sequence`; then (only if each isolated path passes) drop both; optionally add a separate operations-index arm after monitor query audit. Record task insert and state-update WAL bytes, execution time, shared hit/read/write blocks, `n_tup_hot_upd`, index sizes, PostgreSQL CPU-seconds, completed tasks/sec, schedule-to-start p95, workflow p95, and all query-path correctness. Ensure runs include empty and nonempty queue, lease expiry/reclaim, failure/retry, resource constrained work, monitor access, native reconcile, duplicate request/dispatch, rolling compatibility/fallback mode, and rollback recreation.
3. **Settings A/B only after evidence:** first measure container cgroup memory limit/current/peak, PostgreSQL cache hit/read latency, checkpoint/WAL and wait metrics on the isolated system. Then vary one setting at a time against a repeated control; do not infer a memory allocation from Docker VM RAM. Do not raise `work_mem` globally without concurrent query/session accounting.

Accept an index retirement only if every supported query path and recovery invariant passes, no plan regresses into a queue-wide scan under backlog, and repeated runs show a meaningful improvement in write cost or CPU per completed task without worse throughput or p95 latency. If performance differences fall within run noise or path coverage is incomplete, keep the index. Accept configuration tuning only after a measured bottleneck is identified and the same end-to-end criteria improve.

## Independent instrumentation / metrics audit

The working tree contains staged coordinator edits to collector SQL, histogram views, and the PostgreSQL dashboard; I did not alter them. Static review found the intended PromQL labels/counter names align with the collector names (`workflow.postgres.statement.*` translated to `workflow_postgres_statement_*`), and adding calls, rows, and shared hits is useful for distinguishing elapsed time from repeated cached access. Histogram boundaries for admission/capacity wait are now shared with existing latency bounds; the explicit batch-fill boundaries cover 0–32. The currently running deployment cannot provide those new series for the historical window, and the old coarse histogram cannot reconstruct a p95 after the fact. Query text remains truncated to 500 chars, so query ID is the stable aggregation key. Since collector samples are cumulative `pg_stat_statements` snapshots, rate/increase is an estimate subject to resets and scrape interval; compare interval deltas after two or more samples. Shared hits are repeated buffer accesses, not unique buffers, disk reads, or CPU. No runtime performance change is inferred from these instrumentation edits.
