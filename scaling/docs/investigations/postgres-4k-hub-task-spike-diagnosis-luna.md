# `hub_task` spike diagnosis after selected-ID integration

**Finding:** The screenshot is a later burst from two additional 4k runs, not the previously reported run 3. The selected-ID SQL is active, but its second per-ID lateral lookup can still use the broad partial `ix_hub_task_claim_sequence` index and filter on `id` after scanning it. A stale/empty estimate for that partial index reproducibly causes the plan and its amplification; this is the strongest explanation for the index-row spike, with historical per-statement/index attribution still limited by the live collector's missing call/row/hit counters.

## Why a selected-ID statement can still scan the queue index

The implemented query is [`CandidateBatchAdmissionSql` in `HubTaskStore.cs`](../../src/WorkflowCore.Hub/HubTaskStore.cs#L79), called at line 691. Its first `ordered_ids` lateral lookup uses `hub_task_pkey` with `Index Cond: (id = ...)`. In both custom and generic live cost-only plans, the second `picked` lateral lookup instead uses `ix_hub_task_claim_sequence`; its plan node has **no index condition** and applies `id=o.id`, epoch, hub, partition, and eligibility as a filter. The final update still uses the primary key. That partial index is only `(sequence)` with predicate `state IN (0,1) AND attempts < max_attempts` ([migration 022](../../sql/022_hub_claim_index_selectivity.sql#L1)), so an ordered `FOR UPDATE SKIP LOCKED` lookup can visit many eligible sequence entries before rejecting rows whose ID differs from the one selected.

The live idle database had 143,976 task rows, all state 2; `pg_stats` put state `{2}` at 100%, and `pg_class.reltuples` for the partial claim index was zero. Its last autovacuum was 01:43:53.566Z and last autoanalyze 01:43:54.966Z—immediately after the second run's last completion. Those are **post-burst** statistics and cannot establish what the planner estimated during the workload.

I reproduced the plan in an isolated, labeled PostgreSQL 17 container with a 1 CPU / 1 GiB cap. With 144k synthetic task rows, I analyzed the table while the partial index was empty (estimated index tuples 0), then added 44k ready rows without refreshing statistics. The exact selected-ID update with 32 IDs chose `ix_hub_task_claim_sequence` in the second lateral, removed **43,999 rows per loop × 32 loops = 1,407,968** by its ID filter, and returned the 32 selected tasks. It touched 95,833 shared buffers and took 231.354ms; the transaction was rolled back. In a fresh-statistics companion shape with all 144k rows active, the same query used primary-key probes, returned 32 rows in 1.042ms, and touched 838 shared buffers. This synthetic contrast isolates planner sensitivity to stale active-index cardinality; it is not a workload benchmark or CPU comparison.

The existing [plan test](../../tests/WorkflowCore.Scaling.PostgreSQL.Tests/HubCandidateBatchPlanTests.cs#L10) analyzes a representative active backlog before explaining the query, matching the fresh-statistics case. The stale/empty-partial-index condition is the material workload difference: an idle completed table can be analyzed with no active index entries, then churn back into an active queue before statistics reflect that population. The run-time `ix_hub_task_claim_sequence` counter jump and the live/synthetic plans support this as the **likely mechanism** for the repeated spike. Historical planner statistics or an actual plan from 01:42–01:45 were not captured, so I cannot prove the exact stale estimate for those calls.

## Audit, polling, and maintenance are distinct contributors

The benchmark's durable audit is not business execution. [`owner_recovery_lab.py`](../../observability/benchmark/owner_recovery_lab.py#L201) exports every task for a run via `workflow_id IN (SELECT id FROM hub_workflow WHERE run_id=...)`. A cost-only live plan for the second audit uses an index to find its 4,004 workflows, then a **sequential scan of all 143,976 `hub_task` rows** and a hash join. The two run exports coincide with about 279,773 task sequential rows read over the 3-minute range, close to two complete table passes. This explains the smaller sequential-read signal and the large audit buffer-read counter; it does not explain 60M index fetches.

The other read-heavy statement is worker hub discovery (`SELECT DISTINCT hub_id` for due or expired rows), a repeated polling query separate from the selected-ID update. Its three-minute shared-read increase is 40,335 blocks. A current idle cost-only plan combines active ready/claim indexes in a bitmap scan; it returns no rows because the table is now fully completed. Due/expired keyset pages are additional discovery work, while task transitions, attempts, and event inserts are necessary durable execution. Autovacuum/autoanalyze ran at 01:43:53–54 and overlaps the screenshot's final peak. PostgreSQL CPU includes this maintenance and the audit tail, so those costs must not be charged wholly to claim execution.

The postgres process-exporter counter gives **299.41 CPU-seconds** for 01:42–01:45 UTC by Prometheus `increase` (user 252.48s + system 46.93s), or **1.66 average cores**; the one-minute `rate` peak is **3.60 cores** at 01:43:55. The 15-second process-exporter scrape cadence makes `increase` an extrapolated counter estimate. The three-minute CPU scope includes both overlapping workflows, their audit tail, and PostgreSQL background maintenance; the interval clips the first run's start, so dividing by 8,000 completions would only be a coarse interval-normalized proxy, not a per-workflow business CPU cost or a controlled optimization gain.
