# PostgreSQL batch-admission experiment — Luna high

**Date:** 2026-11-15. **Scope:** isolated SQL microbenchmark of production `ClaimCandidateBatchAsync` under synthetic active backlog. This experiment makes no historical production-root-cause, workflow-throughput, or production-readiness claim.

## Corrected result

The active-backlog scan-amplification hypothesis reproduced with the deployed-matching migration/index set (002–027, 029, 030; no 028). In analyzed-statistics baseline plans the task-side scan in `picked` read 2,500 rows and filtered 47,500 for a one-item request; the scan cardinality stayed at 2,500 for requested batches 1, 8, 16 and 32. Under stale active-backlog statistics it read 4,062 and filtered 70,938, with actual active rows increased from 50,000 to 75,000 after statistics were collected. This was an index-backed scan, not a sequential heap scan.

The experiment-only selected-ID rewrite was measurably faster in all 48 paired cells (median prototype faster in every paired comparison). For unprepared Npgsql, analyzed early batch 1 measured 8.436 ms baseline vs 0.251 ms prototype (range 8.388–9.007 vs 0.238–0.360 ms); analyzed late batch 32 measured 9.988 vs 1.969 ms (9.479–11.527 vs 1.927–2.922 ms). Stale-active early batch 1 measured 11.690 vs 0.232 ms (11.528–14.801 vs 0.205–0.267 ms); stale-active late batch 32 measured 13.855 vs 1.899 ms (12.934–17.194 vs 1.763–1.922 ms). The [full 96-arm, 48-pair summary](../../benchmarks/hub-batch-admission-experiment/cell-summary.md) contains per-cell medians and min–max ranges across all batches, early/late IDs, plan modes, and statistics conditions. Two measured samples had physical reads; they are retained as valid outcomes, not verifier failures. The verifier asserts completeness and exact rows, not that the prototype wins or that buffers are warm.

The SQL-rewrite hypothesis is therefore supported on this synthetic workload, but the prototype is **not ready for production code**. Its SQL equivalence and isolated concurrent claims passed; it has not been integrated with the store's transaction-owner fencing, attempts/history writes, rollback protocol, or ambiguous-commit handling. The smallest justified next step is a test-only HubTaskStore integration of the rewrite followed by those store-level tests against the disposable database; no runtime patch is justified by this standalone benchmark alone.

## Plan interpretation

Without migration 028, representative baseline analyzed batch-1 plan nodes were `Hash Join` estimate 1 / actual 1 (1,516 hits), over `Index Scan ix_hub_task_claim_sequence` estimate 19 / actual 2,500 / 47,500 removed / 1,516 hits / 0 reads, joined to one selected JSON row. `Sort` and `LockRows` each saw one row (LockRows 1,519 hits), and the update `hub_task_pkey` lookup saw one row / 4 hits; `ModifyTable` returned one lease / 1,552 hits total. Stale-active had the same broad shape, with task scan estimate 23–24 / actual 4,062 / 70,938 removed. The prototype's representative shape was selected JSON `CTE Scan` into a `hub_task_pkey` stable-ID scan (1 actual row / 6 hits), then a separate primary-key candidate probe below `Sort` and `LockRows` (1 row / 7 hits) before `ModifyTable`; total was 45 hits / 0 reads. It no longer scans the active queue to discover a selected task. Buffer hits increased with requested batch because per-row update work increased, but baseline queue scan was already large at batch 1. Baseline hits per lease were 1,552 analyzed and 2,299 stale-active at batch 1 versus 45 and 47 for the prototype. For batch 32 they were around 87–90 analyzed and 111–114 stale-active baseline, versus 46–48 prototype. Full plan node estimates, actual rows, removed rows, loops, hits and reads are in `cell-summary.md` and raw JSON.

The rewrite materializes selected JSON IDs, resolves stable IDs through the primary key, orders by `sequence`, then applies the original eligibility and `FOR UPDATE OF t SKIP LOCKED` logic per selected ID before update. Actual plans confirm primary-key ID probes rather than assuming a plain LATERAL syntax would force them. No durable `ctid` key is used. Full production `RETURNING` was kept. SQL elapsed is not CPU; this microbenchmark does not estimate workflow completion rate.

## Correctness and limits

Correctness now names explicit different SQL files: baseline SHA-256 `66a6b4d4b70e51c0cee55df59003014e4d58faf51fc8dd12173eaa7a3170e3dc` and prototype SHA-256 `cbe797d7bf777004577a35eb38ab4f2c74eaa1634ff902e1b18d2d0e88918215`; normalized hashes also differ and the command fails closed if either pair is identical. See [`correctness-equivalence.json`](../../benchmarks/hub-batch-admission-experiment/raw/correctness/correctness-equivalence.json). Both admitted 4 of 13 rows with the same returned lease IDs, owner mappings and fields other than transaction-time `lease_until`; 9 rejected rows retained owner/state/attempts/epoch. Fixtures cover due-ready, expired lease with epoch match, live lease excluded with observed epoch 1, future, exhausted attempts, constraints, correct and incorrect per-item capabilities/pins, observed-epoch mismatch and native Runnable eligibility.

Two prototype transactions contended over 24 IDs: the first leased 16 while holding locks; the second submitted 16 in reverse order with 8 overlapping, skipped locked IDs and leased the other 8. Final state had 24 unique owner/epoch leases without duplicate leasing or deadlock; see [`correctness-concurrency.json`](../../benchmarks/hub-batch-admission-experiment/raw/concurrency/correctness-concurrency.json). The corrected no-028 existing PostgreSQL test run passed 17 focused tests against `hub_batch_no028_tests` (candidate batching and unconstrained claims). Those tests exercised the **baseline store**, not prototype owner fencing, history/attempt writes, rollback/ambiguous commit, or integrated transaction ownership. Neither the standalone prototype checks nor baseline tests qualify full store/HA semantics.

Rollback trials create MVCC dead tuple and index versions. Both arms received equal trial counts and alternating order, and autovacuum was disabled on the isolated trial tables, but cumulative version growth, cache warming and buffer-state differences can drift across the sequence; equal starting data and rollback-restored logical task state do not mean identical physical cache/version state at every sample. At capture, `pg_stat_user_tables` estimated 9,576 dead tuples and zero autovacuum runs in each matrix database. Only the experiment's own Docker container and synthetic DBs were started/stopped. No CPU was measured, no whole workflow or external side effect ran, and no production/shared resources were altered. No unresolved failed check remains. During correction, an early expected-lease assertion expected 3 rather than 4 fixture admissions and was fixed then rerun; an initial catalog diagnostic compared a text label to the smallint task-state column and was corrected before catalog/results capture; PowerShell parsing caught a stray patch token in `capture-environment.ps1` and passed after correction; a post-stop Docker format query expected a live port binding and failed because stopped containers expose no binding, after which the independent name/label/status/limit inspect confirmed the retained container was exited. These did not affect benchmark samples.
