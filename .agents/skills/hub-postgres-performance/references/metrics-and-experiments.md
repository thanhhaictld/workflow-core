# Prometheus and workload evidence

## Collect comparable windows

- For an archived report, use its actual cohort identifiers, deployed commit/image, topology, timestamps and raw data if available. Report missing series or snapshots as unavailable. For live local work, resolve hosts and labels from the stack. `make obs-ps` and `make obs-config` show services and settings. Use the same project, Compose and env overrides as the deployed stack, and redact tokens, passwords and connection strings from captured configuration.
- Record UTC workload start/end, first persisted workflow and last completion, Prometheus evaluation step and range selector, SQL snapshot times, and audit/export times. For precise statement comparisons, close the SQL snapshot and CPU accounting before bulk durable exports, or identify and account for export statements. The default `obs-test-4k` target runs k6, then exports and audits. Its whole command time includes those extra phases. Keep any in-run readiness and summary polling visible as workload overhead.
- Save active containers, startup times and metric labels for each run. Exclude stale instance series after rebuilds and deduplicate repeated scrapes of the same process. Preserve the actual sample bounds and split counter deltas at resets and restarts. Handle absent, stale and NaN values as missing data.
- Compare cohort-defined server throughput with the Prometheus completion-rate series. For a fully completed cohort, server workflows/s is completed count divided by `lastCompletedAt - firstCreatedAt` in seconds. Show the bounds and success count. Short cohorts can be shorter than a dashboard rate window, so idle periods, rate extrapolation and scrape cadence affect the plotted mean and peak. HTTP start requests/s measures ingestion. Report incomplete cohorts with completion/failure counts and the observed window.

## Query the signal closest to the suspected stage

Inspect the current [Hub runtime dashboard](../../../../scaling/observability/grafana/dashboards/workflow-hub-runtime.json), [PostgreSQL dashboard](../../../../scaling/observability/grafana/dashboards/postgresql.json) and [collector configuration](../../../../scaling/observability/otel-collector.yaml). Use the Prometheus `/api/v1/query_range` endpoint with URL-encoded PromQL, UTC bounds and a step appropriate to the scrape cadence. Save the raw responses and actual filters. These examples need selectors for the measured deployment when Prometheus serves multiple stacks:

```promql
sum(rate(workflow_hub_workflows_completed_total[1m]))
sum(rate(namedprocess_namegroup_cpu_seconds_total{job="postgres-process",groupname="postgres"}[1m]))
sum by (service_name, service_instance_id) (rate(dotnet_process_cpu_time_seconds_total[1m]))
histogram_quantile(0.95, sum by (le, outcome, history_mode) (rate(workflow_hub_claim_duration_seconds_bucket[2m])))
```

- Completions and starts show the balance between load and drain. Compare ready/leased work, candidate entries/credits/reservations, claim outcomes, batch fill, admission waits and worker in-flight counts on the active transport. If the optional Hub database sampler is off, its durable queue gauges can be absent. Use cohort audit, available trace data or bounded database samples for the missing stage. Check run scope and gauge ownership before summing per-Hub or per-shard backlog series.
- Preserve the relevant dimensions when aggregating histogram buckets, such as `activity_type`, `transport` or outcome. Apply `rate` before summing counters, retain `le` for classic histograms, and include observation counts when interpreting sparse percentiles. Combine compatible buckets before calculating a group percentile. [Prometheus query functions](https://prometheus.io/docs/prometheus/latest/querying/functions/#histogram_quantile)
- The CPU queries above return cores. The PostgreSQL dashboard multiplies this by 100, so 300% represents three cores. The Hub dashboard's .NET utilization panel divides by the CPU count visible to each process. For capacity, compare cores with the actual host/container budget and throttling where available. For efficiency, calculate mean cores as CPU seconds divided by elapsed seconds, and CPU ms/workflow as 1,000 × CPU seconds divided by completions in the same interval. If sampled coverage is partial, label it and avoid a whole-cohort cost claim. State when CPU is container-wide or includes idle/background work.
- The PostgreSQL dashboard ranks collector-exported statement counters. Check the collector's sampling, limits and labels before treating it as exhaustive. Use direct boundary snapshots for exact statement deltas when available.

## Confirm where the workflow spent its time

Use the run ID and persisted timestamps, preferably from the existing [owner-recovery export and audit](../../../../scaling/observability/owner-recovery.md). For activity attempts, join `hub_task_attempt.task_id` to `hub_task.id`. Measure creation-to-claim from `claimed_at - created_at` for immediately eligible first attempts and claim-to-finish from `finished_at - claimed_at`. For scheduled, blocked or retried work, identify when the attempt was eligible if possible and distinguish that wait from intentional delay or retry backoff. Keep retries, unfinished attempts and missing events visible. For native workflow phases, pair `WorkflowStarted`, `WorkflowTaskClaimed` and `WorkflowCompleted` events as supported by that workflow's history. Use a workflow-level distribution for end-to-end latency and stage distributions for localization. Stage percentiles cannot be added to get the workflow percentile.

In the operations-index comparison, the 4,000-workflow cohorts completed at about 83–86/s with the index and 71–73/s after removal. PostgreSQL CPU stayed around 39 ms per workflow. Median workflow completion improved, while p95 activity creation-to-claim rose from about 9–19 s to 30–35 s. Claim-to-finish p95 stayed near 0.25 s. The slower tail extended the cohort. Sequential runs on a growing database left the cause of the extra queue wait unresolved.

## Validate a scaling change

- Use existing evidence first. When a new benchmark is in scope, inspect the [current Compose runbook](../../../../scaling/observability/README.md) and [owner-recovery entry point](../../../../scripts/owner-recovery.ps1). The local `make ups-16` and `make obs-test-4k OWNER_RESULTS=artifacts/<investigation>` commands provide the standard stack and 4,000-workflow workload. Resolve the actual stack and configuration, confirm the intended code is deployed, warm the relevant paths, and save uniquely named runs. `ups-16` builds and recreates services and applies migrations.
- For an authorized isolated benchmark, use `WORKFLOW_HUB_QUERIES_ENABLED=false` consistently if measuring without Next.js monitor queries. Prometheus and Grafana remain available. `WFC_HUB_METRICS_SAMPLER_ENABLED` separately controls the Hub's periodic database sampler. Hold monitor and collector workload, run policy, offered load, VUs, routing, shard/worker settings and database history comparable unless they are the variable under test. Record checkpoints, autoanalyze and vacuum when they differ. Avoid concurrent benchmark jobs on shared capacity.
- For A/B, change one lever, repeat warmed runs and show the observed range. Alternate order when practical. If a suspected regression depends on history or planner stats, compare restored copies of the same snapshot in an isolated environment. Use identical workloads for capacity and regression comparisons, or a stepped offered-load series to locate saturation. Check actual starts, completions, backlog slope and the drain tail at each level. A fixed VU test may offer less load when workflow latency increases.
- Verify persisted completions, failures, retries/extra attempts and audit invariants before interpreting a faster run. Compare each arm's server throughput, tail queue/workflow latency, CPU per completion and statement work per completion, with relevant raw evidence. State which controls or measurements could not be reproduced.
